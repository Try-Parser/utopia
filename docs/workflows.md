# Practical workflows

Start with observable acceptance, actual scope and a target. Use a project profile for commands/environment and release procedures. Load only skills the task needs.

**Engineering:** autonomous-development coordinates; craftsman guides implementation; Frank supplies coder, correctness, QA, security, diagnosis and scribe roles. For a two-file UI correction, use a short brief, focused Docker regression/browser journey and three narrow parallel reviews. Schema/auth changes need contracts, threat cases and wider suites. Both get strict final-version evidence and at most two automatic fix rounds.

**Research:** research-workflow defines the decision, opens primary sources, records dates/provenance, seeks counterevidence and consolidates adopt/defer decisions with a reproducible experiment. A second AI's agreement does not replace evidence or calibrated human judgment.

**Design:** design-workflow uses existing components/tokens, accessible states and a reviewable prototype for substantial changes. Approval follows the user's scope/project rules. Actual browser acceptance includes realistic content, responsive behavior and interactions. Optional design plugins add guidance, not authorization or guaranteed quality.

**AI behavior/evaluation:** ai-evaluation separates development, regression and held-out tasks, grades observed outcomes and reports task success/confidence/latency/cost. The scorer is offline; real model runs need local account access and explicit scope. No invented 95%+ result.

**Resume/delivery:** external checkpoints preserve phases, waits, blockers and remote action IDs. Inspect actual files and jobs before retries. Gate staged content before commit, map committed tree afterwards, then push/deploy only to the authorized target and verify actual delivered behavior.

**Shared knowledge:** global instructions store stable methods. Repository instructions hold concrete contracts/runbooks. Project memory stores scoped durable lessons with sources. Task checkpoints hold unfinished state. Personal histories/credentials stay private; old release facts must be rechecked.

**Iteration:** inspect phase timings and retry/full-suite counts after a slow task. Change one bottleneck at a time and compare comparable tasks. Report active versus external wait time. Track escaped defects/reverts and critical failures alongside speed, not just time-to-push.
